## October 27 follow-up: causes, boundaries and precise file scope

**A — signing fallback.** The old `JWT_SECRET ?? fixed-string` made opaque limiter identities predictable. `security-config.ts` now accepts the exact configured bytes only after a 32-byte minimum, whitespace, obvious-placeholder and low-character-diversity check. These checks cannot prove entropy; Steven must verify genuinely random generation privately. Missing/invalid hosted configuration fails protection with a fixed operator diagnostic and sanitized SERVICE_UNAVAILABLE response. Production/preview cannot use local fallback even with test flags. Only explicitly local development/test may use a process-random key. Existing legitimate configured HMAC identities are retained; no Supabase token was resigned, rotated or invalidated.

Signing/verifier inventory: `rate-limit.ts` signs quota identities/leases, `http-security.ts` uses a process-random HMAC for ephemeral ingress addresses, `report-share.ts` generates random 32-byte share tokens and SHA-256 lookup hashes, and the worker checks an opaque token against its private SHA-256 verifier. `context.ts` still calls Supabase `auth.getUser(token)` for every authenticated context; `ENV.cookieSecret` has no active caller.
